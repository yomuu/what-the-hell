## Deck 1

- id: inc-optimizely
- kind: incident
- title: Optimizely script hijack hits Australian sites
- tag (year): 2026
- region: AU
- attack (suggested): T1195 Supply Chain Compromise; T1056.003 Input Capture: Web Portal Capture (card skimming on payment forms)

Record fields:
- date: 2026-11
- status: breached
- entry: A flaw in Optimizely's signup flow let an attacker add code to customer projects.
- impact: Malicious code ran on websites of 178 organisations, including Australian brands.
- lesson: Treat third-party scripts as your own code. List them and limit them.
- source: Optimizely and Report URI, 2026

Cards:

1. Key terms
   Third-party script: code from another company that runs on your website.
   Card skimmer: hidden code that copies payment card details as people type them.
   Content delivery network (CDN): servers that deliver a company's files quickly to visitors.
   Supply chain attack: an attack on a supplier that then reaches the supplier's customers.

2. What happened
   Around 16 November 2026, an attacker added malicious JavaScript to websites using Optimizely Web Experimentation. Optimizely is a tool for testing changes to websites. Researchers at Report URI found the code on sites of 178 organisations. Optimizely confirmed the breach.
   Sources: [OPT1], [RU1], [TR1], [BC1]

3. How they got in
   Optimizely says the attacker exploited a flaw in its Experimentation account signup flow. The code went into the Project JavaScript field, which runs on every page view. It loaded from Optimizely's own content delivery network (CDN), so browsers trusted it.
   Sources: [OPT1], [BC1], [RU1], [SEJ1]

4. Impact
   Researchers say the code swapped crypto wallet addresses and copied card numbers, expiry dates and card security codes (CVV). It could only read card fields in a site's own forms. Fields hosted by a separate payment provider were out of reach. No count of stolen cards has been published.
   Sources: [SS1], [CN1], [ITN1]

5. The Australian sites
   Report URI's list includes Vodafone Australia, TPG Telecom, HSBC Australia, Rest Super and Betashares. TPG Telecom, which owns Vodafone Australia, paused Optimizely as a precaution. It told iTnews it found no evidence its systems or customer data were compromised.
   Sources: [ITN1], [CN1], [RU1]

6. Lesson: every script is your code
   A script you load from a supplier runs with the same power as your own code. Keep a list of every third-party script on your pages. Remove the ones you no longer use.
   Sources: general lesson drawn from [RU1] and [BC1].

7. Lesson: keep card fields off your page
   Use your payment provider's hosted card fields where you can. In this attack, the skimmer couldn't read card fields hosted by a separate provider.
   Sources: [SS1], [CN1]

Maps: A03 Software Supply Chain Failures (a trusted supplier's script was poisoned). Secondary: A08 Software or Data Integrity Failures (sites ran code they didn't check). NIST CSF 2.0: GV.SC (Supply Chain Risk Management). On Optimizely's side, a signup flaw that reached existing projects suggests A01 Broken Access Control, but Optimizely hasn't explained the flaw, so treat that as tentative.

Check question:
- Q: A skimmer like this one runs on a shop's checkout page. Which card fields are out of its reach?
- Options (logical order):
  - A: Fields on pages served over HTTPS
  - B: Fields in the shop's own payment form
  - C: Fields hosted by a separate payment provider (correct)
- k: 2
- Explanation: Fields hosted by a separate payment provider. The skimmer could only read fields in the site's own forms. Not the shop's own form: that's what it copied. Not HTTPS: it protects data in transit, not from scripts on the page.
- Sources: [SS1], [CN1]

Not on the cards (UNCONFIRMED or conflicting):
- iPhone exploit kits: several outlets say the code pushed iPhone visitors toward exploit kits. These reports trace back to one research write-up, so it's left out.
- Breitbart reports that an Optimizely-recommended setting let a backup copy of the code run on HSBC's site. Single source.
- Report URI found 188 infected snippets out of 1,611 checked. That's a different count from the 178 organisations. The cards use 178 organisations, which most sources agree on.
- The claim that the attacker rebuilt the payload 26 times in one day is attributed to Scott Helme by one outlet only.
- The time Optimizely finished cleaning up (about 8:10am AEDT Tuesday) comes from one source.
- One report says nine sites had Australian domains. Not confirmed elsewhere.
- Optimizely hasn't said how many customer projects were changed or how a signup flaw reached existing projects.

## Deck 2

- id: inc-agent-framework-pypi
- kind: incident
- title: Microsoft agent-framework package poisoned on PyPI
- tag (year): 2026
- region: (none; cloud)
- attack (suggested): T1195.002 Compromise Software Supply Chain; T1552.001 Unsecured Credentials: Credentials In Files

Record fields:
- date: 2026-11
- status: verified
- entry: Two poisoned releases were published under Microsoft's real PyPI project.
- impact: A credential stealer ran on every Python start where they were installed.
- lesson: Pin exact versions. Rotate secrets after a bad install.
- source: Microsoft agent-framework project and BleepingComputer, 2026

Cards:

1. Key terms
   Python Package Index (PyPI): the main public site for sharing Python packages.
   Credential stealer: malware that hunts for passwords, keys and tokens, then sends them to an attacker.
   .pth file: a small file Python reads every time it starts. It can run code.
   Continuous integration and continuous delivery (CI/CD): automated systems that build, test and ship code.

2. What happened
   On 17 November 2026, two malicious versions of Microsoft's official agent-framework package appeared on the Python Package Index (PyPI). They were versions 1.26.1 and 1.26.2, published about 33 minutes apart. PyPI has quarantined both. Version 1.26.0 is the last clean release.
   Sources: [MSGH1], [BC2], [SW2], [THN1]

3. How they got in
   The bad releases came through Microsoft's real project, not a lookalike name. Microsoft hasn't said how the attacker got permission to publish. Researchers say the malicious versions weren't built from Microsoft's source code.
   Sources: [BC2], [SW2], [JF1], [MSGH1]

4. Why it ran without being used
   Each bad release added a .pth file. Python runs import lines in .pth files every time it starts. So the stealer ran even if your code never imported the package.
   Sources: [JF1], [OX1], [BC2]

5. Impact
   The malware hunted for cloud and developer secrets. These included Azure, Amazon Web Services (AWS), GitHub and Docker credentials, plus CI/CD secrets. No count of affected users has been published.
   Sources: [BC2], [THN1], [SOC1]

6. Lesson: pin exact versions
   Pin exact versions in your requirements file, such as agent-framework==1.26.0. A loose rule like >=1.26.0 would have pulled in a bad release automatically.
   Sources: general lesson. The clean version (1.26.0) is from [BC2] and [SOC1].

7. Lesson: removing it isn't enough
   Uninstalling the package doesn't make stolen keys safe. Rotate every secret the machine or pipeline could reach. Then rebuild from a clean environment.
   Sources: [SOC1], [BC2], [JF1]

Maps: A03 Software Supply Chain Failures. NIST CSF 2.0: GV.SC (Supply Chain Risk Management) and PR.AA (Identity Management, Authentication and Access Control: rotating exposed secrets).

Check question:
- Q: You installed agent-framework 1.26.1 on a build server yesterday. What's the most important next step?
- Options (logical order):
  - A: Upgrade to the next release
  - B: Uninstall the package and carry on
  - C: Rotate the secrets the server held (correct)
- k: 2
- Explanation: Rotate the secrets the server held. The stealer ran at startup, so assume they were taken. Uninstalling stops it running again but doesn't undo theft. Upgrading is the trap answer because 1.26.2 was also malicious.
- Sources: [BC2], [SOC1]

Not on the cards (UNCONFIRMED):
- How the attacker got publishing access. A community-filed GitHub issue (#10411) suggests a compromised upload credential. That's not a Microsoft finding.
- "Repacked the clean wheel locally": JFrog's analysis. The cards only say the releases weren't built from Microsoft's source code, which the GitHub issue and JFrog both state. Reviewer: confirm this is acceptable as two sources, or drop that sentence.
- Exfiltration to a webhook: reported in summaries, but I couldn't pin it to two named outlets.
- Version 1.26.2 also requested GitHub Actions OpenID Connect (OIDC) tokens. Reported by research blogs. Left off to keep cards short, but it's a good detail if confirmed.
- A Microsoft maintainer reportedly confirmed removal and an investigation in a GitHub discussion. I couldn't open it.

## Deck 3

- id: inc-cold-relic
- kind: incident
- title: COLD RELIC: one cloud breach used to hit another
- tag (year): 2026
- region: (none; cloud)
- attack (suggested): T1621 Multi-Factor Authentication Request Generation; T1098.005 Account Manipulation: Device Registration; T1656 Impersonation

Record fields:
- date: 2026-11 (Google's case study date; the intrusions ran from late 2025 into 2026)
- status: breached
- entry: Stolen Super Admin credentials, then repeated MFA push prompts until one was approved.
- impact: Staff directory and Workspace data exported, then used to target a second organisation.
- lesson: Use phishing-resistant MFA for admins. Remove unknown passkeys after a takeover.
- source: Google Threat Intelligence Group and Mandiant, 2026

Cards:

1. Key terms
   Super Admin: the top admin role in Google Workspace, with control over every account.
   Multi-factor authentication (MFA) fatigue: sending many sign-in prompts until the person approves one to make them stop.
   Passkey: a phishing-resistant way to sign in, stored on a device instead of a password.
   Impersonation: pretending to be someone the target already knows and trusts.

2. What happened
   On 17 November 2026, Google described attacks by a Russia-linked espionage group it calls COLD RELIC. The group broke into one US organisation's Google Workspace. It then used the stolen data to break into a second US organisation. Neither victim has been named.
   Sources: [G1], [TR2], [THN2]

3. How they got in
   The group had stolen the password for a Super Admin account. It then sent repeated multi-factor authentication (MFA) push prompts until one was approved. Push approvals are a weak form of MFA, because a tired person can tap yes.
   Sources: [G1], [THN2], [CP1]

4. How they stayed in
   Once inside, the group added its own passkeys, backup codes and MFA devices to the account. These kept its access working after password resets. Passkeys weren't the weakness here. The attacker registered its own after taking over the account.
   Sources: [G1], [CP1], [NMI1]

5. Impact
   Using Super Admin rights, the group exported the staff directory and started a domain-wide Google Workspace export. It then posed as a real staff member of the first organisation to approach the second one.
   Sources: [G1], [THN2], [TR2]

6. Lesson: protect admin accounts first
   Give Super Admin accounts phishing-resistant MFA, such as FIDO2 security keys or passkeys. Push prompts can be approved by mistake. Keep the number of Super Admins small.
   Sources: [SO1], [G1]. "Keep the number small" is general least-privilege guidance.

7. Lesson: clean up after a takeover
   Resetting the password isn't enough. Revoke sessions and tokens. Remove any passkeys, backup codes or MFA devices you don't recognise.
   Sources: [CP1], [G1]

8. Lesson: check unexpected contact
   A message from a known contact can still come from an attacker using stolen data. Check unusual requests through a separate channel you already trust.
   Sources: general lesson drawn from [G1] and [TR2].

Maps: A07 Authentication Failures (weak push MFA on a top admin account). NIST CSF 2.0: PR.AA (Identity Management, Authentication and Access Control) and DE.CM (Continuous Monitoring: new MFA devices and bulk exports).

Check question:
- Q: After the takeover, the victim resets the Super Admin password. Why might the attacker still get in?
- Options (logical order):
  - A: The reset doesn't apply to admin roles
  - B: The attacker's own passkey is still enrolled (correct)
  - C: Google Workspace keeps the old password active
- k: 1
- Explanation: The attacker's own passkey is still enrolled. Passkeys and backup codes work without the password, so remove unknown ones too. Not the admin role or the old password: the reset worked, but the attacker had another way in.
- Sources: [G1], [CP1]

Reviewer note: this deck fits the handoff accuracy rule on MFA. Push prompts are phishable and can be approved by mistake. Only FIDO2 keys and passkeys are phishing-resistant. Card 4 makes clear the passkey was the attacker's persistence, not a flaw in passkeys.

Not on the cards (UNCONFIRMED or conflicting):
- Other names for the group (COLDRIVER, UNC4057, Star Blizzard) appear in one summary. Check [G1] before adding them.
- Dates: sources place the first breach in late 2025 and the second in 2026. The cards avoid exact dates.
- One outlet says the approach to the second organisation was on an encrypted messaging app. Another calls it phishing. The card just says "approach".
- The second organisation reportedly used Microsoft Entra ID for single sign-on into Google Workspace. Single source.
- The exact name "Customer Takeout" comes from search summaries of [G1]. The card says "domain-wide Google Workspace export" instead.

# Quick-fire cards (one card each)

1. id: qf-java-version
   Heading: Know your Java runtime
   Text: On 17 November 2026, CISA urged immediate patching of a critical Java flaw, CVE-2026-114938, nicknamed Java4Shell. Run `java -version` to see which Java runtime a server uses. Apps that bundle their own Java need checking separately.
   Sources: [CISA1], [CCCS1], [QL1]. Spell out on first use: Cybersecurity and Infrastructure Security Agency (CISA). The bundled-runtime point is general guidance.

2. id: qf-container-secrets
   Heading: Leaked keys get used in seconds
   Text: Stony Brook University researchers planted Amazon Web Services (AWS) keys in public container images. Bots used one key 7.86 seconds after it went public. Scan images for secrets before you push them.
   Sources: [BC3], [SCW1]

3. id: qf-pin-versions
   Heading: Spot the mistake: a requirements file
   Text: A requirements file says `agent-framework>=1.26.0`. The mistake is the loose version rule. On 17 November it would have installed malicious 1.26.1 or 1.26.2. Pin exact versions: `agent-framework==1.26.0`.
   Sources: [BC2], [SOC1]

4. id: qf-valid-creds
   Heading: Valid logins don't raise alarms
   Text: Uber says about 149,000 people had data exposed through a service provider's stolen credentials. Uber says it wasn't alerted because the attacker used valid credentials. Watch for unusual use, not only failed logins.
   Sources: [ME1], [TR3], [BC4]
   Reviewer note: several outlets name the provider as Fireworks AI, which links to the inc-fireworks-ai draft from 2026-11-17. Uber's letters don't name it, so the card doesn't. The exact figure in Uber's Maine filing is 149,346. Exposed data includes names, driver's licence numbers, dates of birth and addresses.

5. id: qf-incident-not-breach
   Heading: Spot the mistake: "Coles was breached"
   Text: On 16 November 2026, Coles reported a cyber incident to the Australian Securities Exchange (ASX). It's working with the Australian Cyber Security Centre (ACSC). It says it has found no evidence data was taken. "Incident" isn't the same as a confirmed breach.

# Ideas for future weeks

1. Client-side security for web pages: inventorying third-party scripts, Content Security Policy (CSP), Subresource Integrity (SRI), and the PCI DSS 4.0 payment-page script rules (check: requirements 6.4.3 and 11.6.1). Why: the Optimizely attack shows the gap, and web and AppSec roles often ask how you'd stop a card skimmer.

2. Securing package installs and publishing: lockfiles with hashes, PyPI Trusted Publishing, and limiting GitHub Actions id-token permissions. Why: package hijacks like agent-framework keep hitting cloud credentials, and DevSecOps and cloud roles expect you to know these controls.

3. Spotting MFA abuse in identity logs: push-prompt floods, new device or passkey registrations, and bulk exports in Google Workspace and Microsoft Entra ID. Why: COLD RELIC shows what to look for, and SOC analyst interviews often ask how you'd detect an account takeover.
